堂食外卖自取三模式统一订单抽象设计
一、三种点餐模式的业务差异
中餐门店需要同时处理三种点餐模式，每种模式的业务流程和履约链路存在显著差异。堂食扫码：顾客到店入座后扫描桌码，订单绑定桌台，后厨出餐后由服务员传菜，顾客离店时结账或在线支付。外卖配送：顾客在线下单并填写配送地址，系统计算配送费和配送范围，订单由骑手配送到家。到店自取：顾客在线下单后到店取餐，系统生成取餐码，顾客凭码取餐。

三种模式的订单在数据结构上存在本质差异：堂食订单需要桌台字段和就餐人数，外卖订单需要配送地址、配送费、骑手信息，自取订单需要取餐码和预计取餐时间。如何设计一套统一的订单抽象层，使得三种模式共享核心订单流程又能保持各自扩展性，是系统架构的关键决策。

二、订单抽象层的技术实现
推荐的设计方案是订单主表 + 模式扩展表的结构。订单主表记录通用字段（订单号、门店ID、用户ID、金额、支付状态、订单状态），模式扩展表分别存储堂食、外卖、自取的专有字段。订单主表的order_type字段标识订单模式，业务逻辑层通过策略模式根据order_type调用不同的处理策略。

以yshop-drink为例，其点餐模块支持外卖、自取、提前预约、桌台扫码等多种模式，不同场景下的点餐流程通过统一抽象层灵活配置。这种设计使得新增点餐模式时只需增加新的扩展表和策略类，无需修改核心订单流程。

三、库存与出餐能力的统一调度
堂食、外卖、自取三种模式共享同一套商品库存和出餐能力。中餐厨房的出餐能力是有限的，系统需要对三种模式的订单进行统一排队调度。技术实现上，可以采用Redis有序集合（ZSet）实现出餐队列，堂食订单和自取订单按预计取餐时间排序，外卖订单按骑手预计到达时间排序。

库存管理方面，每日备餐量是有限的。系统通过Redis缓存商品余量，下单时通过Lua脚本原子扣减库存，防止超卖。当某菜品售罄时，系统同步更新堂食菜单、外卖菜单和自取菜单中该菜品的状态。源码搭建时，建议将库存调度模块设计为独立服务，通过事件总线与订单服务通信，便于后续扩展和独立扩容。
